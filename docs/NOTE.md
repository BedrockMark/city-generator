# 关键决策与被否决方案

记录格式：日期 · 决策 · 原因 · 被否决的备选及原因。

## 2026-11-01 · 阶段 1（分析）

### D1. 参考图预处理：取首帧 → 识别整数放大倍率 → 降回 1x 原生像素
- 42/46 张参考图是 2x 最近邻放大（`tools/normalize_refs.py` 用 2x2 块一致性检测，>0.95 判定）。
- `simple_resident_complex`、`simple_street_corner` 本身是 1x。
- `condo_and_market`、`garden_warmhouse`、`modular_shop_use_ex`、`shop_on_street`（200x112）是**缩略图**，像素不精确 → 标记为 `thumb`，不参与分析。
- GIF 调色板量化导致颜色偏差（最大约 10/通道），所有匹配都用容差（每通道 ≤20）。

### D2. 地图 = 网格图块层 + 自由放置物件层（实测得出，影响生成器设计）
- 地面**和建筑**都对齐 16px 网格（例：market_on_street 的 Market 建筑恰好落在网格相位上）。
- 车辆、标牌、垃圾桶、长椅等道具多数**不在网格上**（像素级偏移，如 x mod 16 = 5、9、11 ...）。
- 因此分析拆成两步：`grid_layer.py`（每格 base 不透明图块 + 可选 alpha overlay 图块）
  和 `detect_objects.py`（任意偏移的 Singles 精灵匹配，只计“网格层解释不了的像素”）。
- 否决：只用网格匹配 → 漏掉绝大多数道具；只用自由匹配 → 纯色地面类精灵（Ground_Tile_Spot、
  Brake_Marks、autotile 片段）在地面上大量误报（首次试验 market_on_street 出现 312 个物件，其中约 250 个是误报）。

### D3. 网格相位用“有纹理像素”打分
- 纯色沥青这种平坦图块对任何相位都能匹配，会使相位判断失效；只统计与图块主色差异大的像素。

### D4. 地形词表 = 全部 sheet 的图块（不仅是 1_/2_/autotiles）
- 医院、学校等 sheet 自带自己的人行道图块，只用地形 sheet 会导致这些图解释不了。

### D5. 统一的 scene JSON 格式（参考图分析结果与未来生成器输出共用）
- 网格层（tile id）+ 物件列表（sprite id + 像素坐标 + 语义类）。
- 好处：同一套工具可用于“重建参考图验证分析质量”、统计关系、以及检查生成结果是否抄袭/自我重复。

### D6. 参考图分类（`tools/refs_meta.json`）
- street（有道路/人行道的街区）、site（单一场所/自然）、showcase（建筑或素材展示，不是地图）、thumb（缩略图）。
- 同源近重复组：shopping_centre_with_ads / with_parking_lot；garbage_centre_1 / 2；apartment / smaller_apartment_ex。
  做任何留出验证时同组必须一起划分，否则抄袭检测和评估会被高估。

### D7. 人物按图层独立检测，主题由“出现场所”确定
- 人物是 5 层合成，组合数巨大，无法整体匹配；改为分别匹配服装和配饰图层的帧，只在场景重建解释不了的像素上匹配。
- 服装没有主题分类：用“在哪张参考图、什么物件旁边出现”来打标签，再用目测补充（`tools/character_themes.json` 注明证据来源）。
- 否决：只看预览图目测打标签。16×32 太小，西装、校服、制服容易看错，比如组 30 看起来像劫匪，实际是深色卫衣，劫匪感来自 Balaclava 配饰。

## 2026-11-01 · 用户对阶段 1 问题的答复（阶段 2 的依据）
- 主题：商住混合街区作为起点。
- 区块：内部尺寸**和形状**都随机。参考尺寸 28×20 格（用户写的是“280 cells”，但 28×20=560；先按 28×20 的尺寸理解，已在汇报中指出）。整张图的尺寸自由，四周可以加任意可选的道路 / 背景。
- 人物：放入合理的静止帧人物。
- 语言：TypeScript 为主；其他语言可以用来加速或增强，只要最终地图能在 Phaser+TS 中显示。
- 存档：导出功能一次给出所有需要的文件；用户会把好的放进 `references/holdout/` 并改名加描述。反例同样处理，另附同名 `.md` 说明问题。
- 参考图变更：condo_and_market、garden_warmhouse、shop_on_street 换成了原尺寸版本；modular_shop_use_ex 删除；新增 soccer_court。
  - condo_and_market 与 market_on_street 共享 Market 街角 → 近重复组 `market`。

## 2026-11-01 · 阶段 2（原型）

### D8. 生成器用 TypeScript 写，在浏览器里运行；Python 只做分析和评估
- 重新生成是即时的，导出的 scene JSON 可以直接交给 Python 工具评估。
- `app/scripts/batch.ts`（Node 批量生成）和 `tools/render_generated.py`（Python 渲染）让我不开浏览器也能快速迭代。
- Phaser 导出与 Python 渲染逐像素对比：99.5% 完全相同，其余差值 ≤8。
- `app/scripts/shots.ts` 用系统自带的 Edge（playwright-core，不额外下载浏览器）点击真实的导出按钮来截图。

### D9. 3/4 视角下所有立面都朝南
- 北侧街道看到的是楼的屋顶和背面，这是正确的视觉。南侧街面是主要的“热闹面”，北排楼的正面朝向内院。

### D10. 街区形状 = 内部形状膨胀出人行道，再膨胀出道路
- jog：靠纯膨胀得到错位街道。
- notch：外圈直街加缺角处的环路，形成小岛街区和 T 字路口。
- 否决：让缺角直接并入道路，结果是大片沥青空地，不像城市。

### D11. 统一的建筑打包器（main 和邻近街区共用）
- 从最低行开始，底边对齐放楼，面朝背面的楼留 2 行前院；非临街的楼只能是住宅。
- 邻近街区在扩展网格上打包（画面外的虚拟格子按“到道路的距离”延续），这样被裁切的街区也有楼。
- 否决：固定的“南排 / 北排”两段式。不规则形状下会留下大片空院。

### D12. 内院必须变成功能空间
- 按大小和是否临街，变成停车场、横向车位或花园（带围栏和门）；服务杂物只作为点缀，放在剩余角落。
- 否决：内院只铺石板放几个盆栽。看起来就是反例的空地。

### D13. 自我重复改用“物件星座”指标
- 参考图约为 0，反例 0.64，区分很清楚。
- 否决：4×4 图块窗口。人行道纹理本身是周期性的，生成结果会被误判为 0.3。

### D14. 节奏带要“有拍子但不机械”
- 加 ±3px 抖动，12% 的位置随机替换，遇到事件就打断。邻近街道的设施更朴素，有的街道完全没有。
- 完全规则的树–灯交替会让物件星座重复率升到 0.135，比参考图的最大值还高。

### D15. 相邻的模块楼可以共用颜色和高度形成连续立面，但底商不能是同一家族
- 两家一样的冰淇淋店并排，正是“复制”的观感。

## 2026-11-01 · v0.3.0（处理 v0.2.0 的评价）

### D16. 建筑的碰撞体积 = 屋顶大小（用户要求）
- footprint 是精灵底部的 `foot` 行：模块楼用屋顶精灵的高度，单体建筑取 round(h/2)，并限制在 [3, h-2]。
- 精灵在 footprint 以上的部分，压住的是楼后的地面（`plan.hidden`），这部分地面算作内院，要放后院内容。**已被 D38 取代**：楼后的地面不再特殊标记。
- 打包时建筑之间仍然按整张精灵不重叠：否决了“后排楼可以被前排楼挡住一部分”的做法，以后可以再试。**已被 D38 取代**：打包只按底层占地。
- `Placed.solid` 记录 footprint 顶部的 y。查看器的虚化模式（G）把 solid 以上的部分画成 28% 不透明度；导出时同时给出普通 PNG 和 `_ghost.png`。

### D17. 人行道通行带（keepClear 'walkway'）
- 每条路缘段在“路缘设施线”和“楼前设施区”之间留一条 8–12px 的带，物件不能放进去，人可以。
  - 南侧：curb-22..curb-14；北侧：curb+16..curb+28；竖向街道按人行道宽度设偏移。
- 所有路缘设施都要求 footprint 的四个角都落在 walk/nwalk 格上（`putFoot({ walk: true })`）。
- 楼前设施贴着立面放（foot = bottom+10，depth 9），放在门两侧；门前禁放区延伸到路缘。
- `free()` 可以只忽略某几类禁放区：`ignoreClear: ['walkway', ...]`。
- 新增的评估指标：
  - 设施站在车道上：v0.2 每 30 个种子 85 个 → 0；
  - 人行道中线被挤占：21.8% → 9.7%。
  - 否决了“人行道被切断次数”这个指标：2 格宽的人行道几乎不会被完全切断，这个指标对用户说的“挡路”不敏感。

### D18. 内院逐块分配（yard.ts）
- 空地先在可见地面上从大到小切矩形，再切被楼挡住的地面。每个矩形按规则分配用途：
  - 楼前退出 ≤3 行，且南侧临街 → 楼前空地（按楼的类型放内容）；
  - 足够大，并且能找到车道 → 停车场；
  - 最短边 ≥3 且面积 ≥15 → 花园（最多 2 个）；
  - 1–2 格宽、两侧都不是人行道、南侧临街 → 过道（保持空，最里面放垃圾桶）；
  - 细长 → 绿化带或盆栽；
  - 其余 → 杂物角（最多 2 个）；被挡住的地面 → 后院（D38 起取消，楼后的地面和别处一样分配）。
- 否决：v0.2 只处理最大的一块空地，剩下的边角就是灰色空地（用户：“高层后全空”）。
- 否决：可见地面和被挡地面一起切矩形，结果停车场的通道画到了楼的下面。

### D19. 停车场必须有车道
- findDrive：从停车场边缘找一条 2 格宽的直线路径，穿过（未被挡住的）内院格和人行道格到达马路，取最短的。
  - 南侧对着停车场的任意列；东西两侧对着通道行；北侧只能从车位条的空余端进来。
- 车道经过的人行道格改成 'road'，并重绘周围的 autotile，路缘缺口就自然出现了。所以 yardSpaces 必须在 curbRuns 之前执行。
- 找不到车道就不做停车场。

### D20. 路缘设施去机械化
- 路灯单独布置：每 8–12 格一盏；主街区 70%、邻近街区 35% 的街道有路灯。东侧人行道（马路在东边）用灯臂朝右的 Street_Lamp_1/2/3，西侧用灯臂朝左的 Street_Lamp_4。
- 树间距在 3–7 格之间加权随机，15% 的位置缺树。北侧窄人行道不种树（树冠会盖住车道，对应用户的“延伸到车道上”）。
- 花箱和护柱改成在街角附近放一小组，不再整条街排满。
- 否决：v0.2 的固定拍子（树–灯交替）。用户评价为“完全重复”。

### D21. 长凳朝向（实测）
- Bench_1/2：面朝南（观众方向）；Bench_7：背面，面朝北。
- Bench_3/5：靠背在右侧，面朝西（左）；Bench_4/6：靠背在左侧，面朝东（右）。v0.2 把这两组弄反了。

## 2026-11-01 · 阶段 4（可解释与标注，v0.4.0）

### D23. 解释信息只写不读，画面逐像素不变
- `gid / reason / anchor`、小组表、区域表、决策轨迹都只写进场景 JSON，生成器自己从不读回。所以加解释不会改变任何放置。
- 验证：固定的 200 个回归种子（`app/scripts/regression_seeds.json`：用户反馈过的 12 个种子 + 1..N，只增不改），对比“画面签名”（地面图块 + 绘制列表）。v0.3.0 → v0.4.0：200/200 完全相同。
- 建筑 id 仍是 `b13144` 这种大数字：打包时被拒绝的候选建筑也会占用编号。而 id 又是店门随机流的 fork 标签，重新编号会改变画面，所以保留。

### D24. 随机决策统一经过 `choose(label, ctx, options)`，抽法与原来的 pick / weighted / chance 完全相同
- `options` 可以是数组（均匀）、`{ weights }`（加权）或 `{ p }`（是 / 否）。另有 `count()`（数量）和 `order()`（洗牌）。转换调用点不改变随机数消耗，所以画面不变。
- 原来的 `pick / weighted / chance / shuffle` 仍可用，但会计入 `trace.unlabelled`。回归检查要求它为 0（目前为 0）。
- 不记录为决策的：位置、间距、抖动（`int / range / jitter`）。它们是几何参数，不是选择。
- 地面纹理（沥青变体）和人物的身体 / 眼睛 / 发型用 `tex()`，只按标签统计次数，不逐条记录。否则每张图有几千条记录。
- 被拒绝的提议（打包时放不下的候选建筑）：`mark()` / `reject()` 删掉它们的决策，只在 `trace.rejected` 里计数。否则一张图有 14 万条决策、22 MB；现在约 1,200 条、整个场景 JSON 约 300 KB。
- `fork(label, ctx)` 给每条随机流登记上下文（店铺类型、路缘段朝向……），存在 `trace.streams` 里，不在每条决策里重复。阶段 7 按“流上下文 + 决策标签”重新加权。
- 否决：自动从调用栈推断标签。不稳定，代码一改标签就变，无法跨版本学习。

### D25. 小组 = 一次“出现理由”的实例
- `sb.group(type, reason, { id?, anchor })` 返回 gid：有自然 id 的用 `type:id`（`front:b7`、`curb-trees:run3`、`bld:b7`），否则用 `type#n`（`bus#0`、`crossing#2`）。
- 锚点是带坐标的引用（门、横道、路缘段上的点、车道口、桌子……），查看器从物件画连线到锚点。物件可以覆盖小组的锚点（例如椅子锚到桌子）。
- 约 27 个/图的小组没有成员：决策说“放”，但所有位置都被约束拒绝了（最多的是路灯：一条街抽中有路灯，却一盏都放不下）。保留在 JSON 里，作为阶段 5 的诊断信息；查看器不显示空小组。

### D26. 区域层回答“这里为什么是空的”
- 区域来源：禁放区（门前、通行带、横道口、巷子、公交站台、车道、停车场通道、花园小路、过道），内院分配的每个矩形（包括“零碎空地：朴素铺地”），每条路缘段（抽到了什么设施，包括“不放”），车行道和横道，巷子 / 广场 / 小岛。
- 悬停空地时按“禁放 → 街区开口 → 内院 → 路缘段 → 马路”的顺序列出覆盖它的区域；没有区域时显示格子类别。

### D27. 标注存储：开发服务器直接写进仓库
- vite 插件 `/api/labels` 把标注写到 `references/labels/v<版本>/seed<种子>.json`，第一次标注时同时存一份场景 `<stem>.scene.json`（带解释和决策轨迹）。所以以后的阶段不用重新生成，就能读到用户标注的东西。
- 每条标注记录：版本、种子、创新度、完整生成参数、好 / 坏、预设标签、自由文字，以及目标（矩形、涉及物件的 id / 精灵 / 坐标快照、gid、区域 id）。物件快照让标注在后续版本 id 变化后仍能对上。
- 没有开发服务器时暂存在 localStorage。导出时附 `_labels.json` 和 `_annotated.png`（3 倍放大，文字清楚）。
- 否决：只靠导出下载。用户要手动挪文件，容易丢标注，而且标注和场景会分开。

### D28. 标注层用 Canvas 2D 叠加，不用 Phaser Graphics
- 同一段 `drawOverlay` 既画屏幕叠加层，又画导出的 `_annotated.png`。文字用系统字体，在任何缩放下都清楚。
- 查看器可以拖入场景 JSON（导出的、或标注时存下的）原样查看，用来复查样本。

## 2026-11-02 · 阶段 5（合理化后处理，v0.5.0）

### D29. 约束在生成完的场景上事后判定，场景和参考图共用一套
- `rational/world.ts` 把场景或参考图（`tools/export_refworld.py` → `work/refworld/`）转成同一种“世界”：地面类别、建筑碰撞体积（D38 起不再有“楼后被挡住的地面”）、物件的脚点 / 占地 / 外框、门、区域。约束只读这个视图。
- 生成器在放置时把占地写进 `Placed.fp`（只写不读，画面不变）。
- 否决：在生成器里加检查。那样又回到“给生成器加规则”，而且没法在参考图上测，也没法单独开关。

### D30. 功能连通图：4px 栅格、收缩 1 格；根 = 人行道 / 地图边缘 / 门
- 人行道和地块可以走，车行道不能走（车道口和斑马线可以），建筑碰撞体积和物件占地会挡路；可走区域再收缩 1 格，人要 ≥12px 的空隙。
- 场所 = 内院分配的每块 + 巷子 / 广场 / 小岛 + 街道 + 其余地块；共享 ≥8px 可走边界就连一条边。
- 否决 16px 格：1 格宽的过道、两件物件之间的缝都量不准。否决只看格子类别：看不到物件堵路（种子 33：广场的长椅–树–长椅一排把楼门围死）。

### D31. 约束是数据；修复只删、降级、改地面
- 每条约束 = 规则种类 + 参数 + 严重度 + 修复方式 + 状态。`docs/CONSTRAINTS.md` 由代码生成，附生成图和参考图上的通过率。

### D47. 强制决策与局部 A/B 出题
- 决策身份 =（流, 标签, 第 k 次调用），被丢掉的提议里的调用也计数；`opts.force` 照常消耗一个随机数再返回指定选项，选项不在时记 `forceMissed`。
- 候选得分相同时用 `ab/<种子>` 随机流打乱再稳定排序：按轨迹顺序，所有“邻近街区换楼”的大改动排在前面，30 次试探全用在它们身上。
- 框之间“相距 ≥ 16px”= 两个矩形之间的欧氏间隙（`diff.ts` 的 gap）。代价：斜对角每个方向约 12px 的框也算合格。
- 试探上限仍是 30 次（设计），另加约 10 秒的软时间预算：花完后小题凑够 4 处就停，不够 4 处继续试到上限；大题找不到大改动就改出小题。原因：设计的“3–8 秒”假设一次生成约 250ms，实测约 0.9 秒，30 次要 10–30 秒。结果：平均每题约 10 秒，最长约 14 秒。代价：每题的改动可能少一些；预算按墙钟算，不同机器试到的候选可能不同，但题目本身（种子、选项、改动）总能重现。
- 不加“便宜的无影响预判”：放置为空、没有子流的候选里 38% 仍会改变画面（如 `cars.parked`、exp-01 的 `roof.ac`）。
- 手动出题时，选中的改动看不出差别就提示“这处改动看不出差别”，不偷偷换成自动题。
- A/B 题一律不开 exp-02（整体修图），否则重新打包会把每处单一改动放大成整图变化。

### D48. 创新度：只有“被创新度改变了选择”的零次数贴图才算 `novel`
- 权重 × (1 + 创新度 × 3 × 稀有度)，在偏好乘子之后，只消耗一个随机数；创新度 0 走原路径。
- `novel` = 选中的贴图在参考图和 holdout 里次数为 0，**并且**同一个随机数在不乘创新度系数时会抽到别的选项。按设计的字面意思（选中的零次数贴图都算）会标出 43% 的物件（参考图只有 21 张，大部分贴图次数为 0），金框没法“一眼看出”，评判器还会在默认创新度下把 43% 的物件排除出 `d.*` / `p.*`。现在默认创新度下约 2% 的物件是 `novel`。
- 每条 `novel` 记录最多标一个物件（这个流上第一个还没标的、键相同或属于该部件族的物件）：建筑的选择共用街区的一个流，按“流 + 键”匹配会标出 52% 的楼。代价：金框偶尔落在用了同一部件的相邻楼上。被丢掉的提议里的 `novel` 也一起丢掉。
- 默认创新度 0.10 让 200 个种子的画面全部变化：创新度只要改变一次贴图选择，贴图尺寸不同，后面的打包和放置就全部连锁变化。用户在阶段 4 确认过默认 0.10，设计第 5.5 节也预期会变化；接受，写进报告（如果你想让默认画面稳定，可以把默认降到 0）。
- `repair.test.ts` 种子 2 的用例固定在创新度 0：它测的是修复机制，不是创新度。
- 性能：偏好 / 创新度的钩子第一版让每次生成慢一倍（约 1.2 秒），缓存每个贴图的稀有度、重复的选项列表复用系数后约 0.7 秒（关时约 0.65 秒）。

### D68. 随机混入从生成器移到查看器（v0.7.8.2）
- 用户 2026-11-07：最终目标是逐个区块生成、衍生出无限世界。问 0.7.8.1 在区块内部随机抽特色街区会不会有不可控的影响、做衍生世界时能不能单独定每种区块的概率。看了分析后：“将随机层给到展示器，解耦生成器和展示器，我后面会希望实际应用的大城市生成器明确传 district，不应该在内部随机。”
- 分析（为什么不该在区块里抽）：
  - 每个区块独立抽 20%，没有空间关系：一片 10×10 的区块里约 20 个地标、3 家医院，可能两家医院挨着。这类分布（片区、同类间距、配额）只能由看得见邻居的世界层来定。
  - 特色街区按园区定街区大小，会超出普通街区的范围（普通 W ≤ 40、H ≤ 28；学校宽到 47、高到 30，警察局 46，医院 42）。区块世界里路网要先定，街区尺寸由外面给，和“楼决定街区大小”冲突。这个问题这次不修，做世界层时要先解决：生成器要能在给定的尺寸里放下地标，放不下就换一种或退回普通街区。
  - 抽签走 `choose`，会经过偏好学习的调整：以后要是学出 `district.*` 的乘子，混入概率会悄悄偏离。
  - 种类表增删一项（比如以后加宫殿花园）、改概率，都会让一部分种子换种类。
- 做法：
  - 生成器：`district` 只能是七种之一或不传（= 普通街区），从不自己抽；`'none'` 去掉；不认识的值直接报错（以前 `isDistrict` 用 `in`，`'constructor'`、`'toString'` 也算街区，传进去会崩溃；改成 `Object.hasOwn`）。`mixedDistrict`、`districtChance` 删掉。
  - 查看器：`src/viewer/mix.ts` 的 `mixDistrict(seed, mix)`，`DistrictMix = { chance, weights }`：概率和每种的权重由调用方定，默认 `DEFAULT_MIX`（20%，七种一样）。还是用流 `<seed>/district/mixed`、同样的抽法，所以查看器里每个种子的画面和 0.7.8.1 完全相同。菜单不变：“普通街区” = 随机混入，“只要普通街区” = `d=none`（只是查看器的状态），选了种类就传种类。查看器把抽到的种类明确传给生成器，所以标注里存下的 `options.district` 就是画面实际的种类，重放不依赖混入规则。
  - 顺手修：`sceneStem` 没带 district，同一个种子的普通街区和学校会存成同一个 `seed1.scene.json`（标注保存场景时后一个不写，区域标注会和错的场景比较）。现在加 `_d<种类>`；以前的标注都没有 district，文件名不变。
  - `labeltests.ts` 去掉“0.7.8 以前的标注按 none 重放”的版本判断：不传就是普通街区。`deadend.test.ts` 同样去掉包装。
- 被否决：在生成器里加 `districtWeights` 选项（我第一轮提的）：仍是区块内部随机，用户明确不要。
- 结果：生成器默认 200/200 和 v0.7.8 普通街区相同（`work/regress/v078-normal` → `work/regress/v0782`）；查看器混入 + 明确传种类 200/200 和 0.7.8.1 默认相同；标注测试和以前一样（坏 37 已解决 / 7 仍存在，好 19 保持 / 9 被改动）；53 项测试通过（新增 `src/viewer/mix.test.ts`，`npm test` 也跑 `src/viewer/*.test.ts`）。

## 2026-11-11 · v0.8.0（世界层和街区窗口）

### D73. 世界层局部可算：坐标散列，不用有序的随机流
- 世界层（`app/src/world/`）的每个随机决定都是 `hash01 / hashInt / hashPick(seed, 标签, 坐标…)`（`hash.ts`，和 `gen/rng.ts` 同一种 cyrb128 混合），不从一条随机流里按顺序取数。分区噪声的格点、主干道的偏移 / 宽度 / 错位、每一刀、横道、铺地都按坐标或街区 id 取。
- 原因：无限世界按需生成，同一块地可能在任何顺序、从任何相邻的区域被请求，结果必须一样。有序的流要从原点算起，或者取决于先算了哪块。
- 缓存（主干道格的街区表、生成好的街区）可以有，但结果和不缓存时逐项相同（测试：清空缓存后反过来的顺序算一遍）。
- 被否决：每个主干道格一条 `Rng(seed).fork('world/…', {i, j})` 流（spec 3 的原话）：格内的切分要按顺序取数，同一格内仍然局部，但散列更简单，也能在格内任意位置单独取值。

### D74. 马路格归离它最近的人行道所属的街区，路口不单列
- 每个马路格按切比雪夫距离归最近的人行道格所属的街区，一样近时取 id 小的。路口格也这样归属（spec 2.3 原来写路口归世界层）。
- 原因：这样每个格子都恰好有一个街区负责，街区只在自己这半边车道上停车、放井盖；路口不单列就不需要单独的“世界层物件”，本里程碑世界层不在马路上放任何物件。横道、虚线是地面，由世界层画。
- 被否决：路口归世界层（spec 原文）：要另外判定路口格的范围，世界层还得决定路口上放不放东西；现在没有这种需求。

### D75. 窗口是生成单位：`generateBase` 的可选参数，不复制流水线
- 一个街区的窗口 = 占地外包框四周加 `WINDOW_MARGIN`（14）格，翻译成现有的 `Layout`（`app/src/world/window.ts` 的 `blockLayout`），交给 `generateBase(seed, opts, win)`。有窗口时不调 `makeLayout`、`planNeighbours`、`nfronts`、`island`，其余流水线完全一样；最后丢掉 `ownerCell` 落在别的街区格子上的物件和区域。
- 原因：生成器的规则都在一条流水线里，复制一份城市版会两边分叉。不传窗口时代码路径不变，200 个回归种子画面和约束记录逐项相同。
- 窗口代码放在 `app/src/world/window.ts`，不是 spec 4 写的 `app/src/gen/window.ts`：`gen/` 不依赖 `world/`。
- 被否决：城市模式单独写一条生成流水线：规则会和单街区模式分叉，单街区的修改到不了城市。

### D76. jog 街区：L 形一侧可以继续被平行的直刀切开
- 一刀以 `JOG_CHANCE`（25%）的概率在 `JOG_AT`（30–70%）处错开 `JOG_STEP`（2–4）格。错开的一侧（L 形）还可以被平行于这条支路的直刀继续切开，L 形总留在其中一边，最后成为一个 jog 街区（两个共边的矩形）；每个街区最多错开一次；L 形不能被垂直的刀切。
- 原因：要求 L 形一侧马上是叶子时，只有最后一刀能错开，实际比例只有 0.054（测试下限 0.1）。现在约 0.121（30 个种子 × 7 × 7 个主干道格）。也更接近计划里的“错开后两侧的每个矩形仍可切开”。
- 被否决：L 形一侧必须马上是叶子（太少）。观感留给用户看（v0.8.0 报告第 6 节）。

### D77. 小物件随窗口的形状变化，暂不改（v0.8.0-hotfix1 已修，见 D82）
- 现有生成器的部分随机流按窗口里的相对坐标取标签（花园位置、路缘设施、停车、区域的 `x0, y0`），马路 / 人行道 / 横道 / 车的一部分抽签在整个窗口上按顺序进行。窗口放大一圈时，楼不变，但花园、路缘设施、停的车会换。
- 决定：不改生成器。每个街区的窗口只由（种子，街区 id）决定，所以结果仍然确定、局部可算。测试改为：窗口放大 4 格时楼（种类 + 世界位置）相同，两种窗口下归属过滤都成立。
- 原因：spec 4 没有要求和窗口大小无关；按世界坐标重新取标签是对生成器的大改，单街区回归有风险，不属于这个里程碑。
- 代价：以后改 `WINDOW_MARGIN` 或改成按世界坐标取标签，所有街区的小物件都会变（v0.8.0 的城市画面不能保持）。候选做法：做 `getChunk` 时按世界坐标取标签。

### D78. 世界层的数字全在 `config.ts`，派生的也从常量推出
- 计划的各任务里写了一些字面量（分区第二层噪声的 3 倍间距和 0.5 权重、横道的最短直路 8 格、分析 / 绘制的外扩 16 格、区域外扩 6 格、路宽集合 {5, 7, 9}、窗口的 `sw2` 3、横道长 2 和间隔 0–1、虚线最短 6）。全部做成 `config.ts` 的具名常量（`ZONE_OCTAVE`、`CROSSING_MIN_RUN`、`ANALYSIS_PAD`、`REGION_PAD`、`ROAD_WIDTHS`、`WINDOW_SW2`、`CROSSING_LEN`、`CROSSING_GAP`、`DASH_MIN_RUN`）。
- `ROAD_WIDTHS` 由 `ARTERIAL_WIDTHS` + `STREET_WIDTH` 推出来；`REGION_PAD = ceil((最宽主干道 + ARTERIAL_JOG) / 2)`（= 6）。改宽度时它们跟着变。
- 原因：spec 3.8（用户 2026-11-11）：概率、权重、尺寸只在 `config.ts` 里，改一处即生效；这条比任务说明里的字面量优先。

## 2026-11-11 · v0.8.1（区块 API、Worker 池、查看器城市模式）

### D84. 区块地面取拥有者街区的窗口地面，不重画世界地面（v0.8.1）
- `assembleChunk` 里每个街区格的地面直接取拥有这个格子的街区的窗口地面（`CityBlock.ground`）（街区拥有的格见 D74、D75）；只有没有街区可用的格（`missing`）才用 `paintGround` 的世界地面。
- 原因：重画世界地面每个区块要 210 ms；取窗口地面的组装约 53 ms（单进程，街区已缓存）。窗口地面本来就是世界地面加街区自己的改动；接缝检查（`cityregress.ts`）验证区块并排和 `assembleRegion` 整块逐格相同。
- 被否决：
  - 主线程组装区块。
  - 每个 Worker 独立 `getChunk`：边界上的街区会在好几个 Worker 里重复生成（一个街区约 0.5–0.8 秒），总工作量翻几倍。

### D85. 查看器 Worker 两步：先生成街区，再组装区块（v0.8.1）
- `cityqueue.ts` 调度、`pool.ts` 的 Worker 池、`city.worker.ts` 三种消息（`block` / `chunk` / `scene`）。
- 第一步：视口里每个区块需要的街区，按离中心的远近交给空闲 Worker 生成，结果 `trimBlock` 裁剪后回到主线程缓存（`BLOCK_CACHE`）；第二步：街区到齐的区块带着这些 `CityBlock` 发给 Worker 组装。街区只生成一次，被几个区块共用。
- 换种子 / 退出城市模式时 epoch 加一，旧结果丢弃；失败的街区在同一个 epoch 里不重试（区块用世界地面，`missing` 记录）。

### D86. 城市标注的存放键 `storeKey`（v0.8.1）
- 城市里的街区标注用 `storeKey(sc) = w<种子>_<街区id>`（文件名安全化），超过 80 个字符时取前 71 个字符 + `_` + 8 位十六进制散列；场景文件是 `seed<storeKey><选项>.scene.json`（`labelSceneName`，上限 80）。导出文件仍用 `sceneStem`。
- 开发服务器对不安全的场景名返回 400（单街区也一样：约 60 个字符以上的单街区种子，标注退回 localStorage，不再存一个缺场景文件的标注。取舍：宁可不存，也不要标注指向不存在的场景）。
- `storeKey` 的文件名安全化是简单替换，只差标点的世界种子（`a,b` 与 `a_b`）会撞同一个键；计划规定如此，未处理。
- 原因：街区 id 含 `/`、`,`，不能直接做文件名；不同世界种子的同一街区 id 不能互相覆盖。
