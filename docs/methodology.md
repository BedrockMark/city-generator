# 方法总结：训练（分析与校准）与生成

> 截至 v0.4.0（2026-11-01；v0.4.0 只加了第 2.4 节的可解释与标注，生成逻辑同 v0.3.0）。详细依据见 `docs/ANALYSIS.md`、`docs/STAGE2.md`、`docs/v0.3.0.md`，决策编号 D1–D22 见 `docs/NOTE.md`。

## 0. 一句话

本项目**不训练神经网络**。参考图只有 46 张，而且都是局部画面，不够让模型学出结构；生成式模型也无法保证像素完全由素材拼成（见 `ANALYSIS.md` 第 5 节，方案 D 已否决）。

所以这里的“训练”指的是**离线分析参考图**：用 Python 把每张参考图反解析成结构化场景，统计出尺寸、物件间关系、距离和节拍，用这些数字校准手写规则的参数，同时给评估指标定基线。

“生成”是**叙事优先的分层程序生成**：TypeScript 写的规则管线，由种子驱动，在浏览器 / Phaser 里即时运行。

```
参考图 ──预处理──► 反解析成 scene JSON ──► 统计（尺寸 / lift / 距离 / 节拍 / 人物）
                                              │
                         手写小组语法 ◄────────┘ 校准参数
                              │
种子 ──► 分层生成管线（TS）──► scene JSON + PNG ──► 自动评估（抄袭 / 自我重复 / 空地 / 挡路）
                                                     └──► 用户评价 remarks ──► 下一版本
```

两边使用**同一种 scene JSON 格式**（网格图块层 + 自由物件层，D5）。所以分析工具可以直接用来检查生成结果。

## 1. “训练”：从参考图中提取规律

全部脚本在 `tools/`（Python 3.12 + uv），一键运行：`tools/run_analysis.sh`。中间产物写到 `work/`。

### 1.1 预处理
- GIF 只取首帧（`extract_frames.py`）。
- 检测整数放大倍率，降回 1× 原生像素（`normalize_refs.py`）：用 2×2 块一致性检测，>0.95 判定为 2× 放大（D1）。
- `refs_meta.json` 给每张图记录：
  - 地图有效区，用来裁掉 UI 边框和侧边素材栏；
  - 类型：street / site / showcase / thumb；
  - 近重复组。近重复组在任何留出验证中都必须一起划分（D6）。
- GIF 调色板会让颜色偏移，所有像素匹配都用每通道 ≤20 的容差。

### 1.2 素材编目
- `build_tile_index.py`：把所有整合 sheet 切成 16×16 图块并去重，得到约 4.3 万个唯一图块。地形词表用全部 sheet，不只用地形 sheet（D4）。
- `build_catalog.py`：编目约 5,400 个单张精灵，记录素材包、名称、尺寸、不透明包围盒和重复关系。
- `autotile.py`：整理 GMS 47 格 blob autotile 表（路缘、草地边缘）。

### 1.3 场景反解析（把像素还原成“用了哪些素材、放在哪里”）
实测发现地图分两层：地面和建筑对齐 16px 网格，道具多数按像素自由放置（D2）。所以反解析也分两步：
1. **网格层**（`grid_layer.py`、`grid_objects.py`）：
   - 先求网格相位，打分时只用有纹理的像素，避免纯色沥青让任何相位都能匹配（D3）；
   - 再给每格识别 base 图块和 alpha overlay 图块。
2. **自由物件层**（`detect_objects.py`）：
   - 在网格层解释不了的像素上，用掩码 SSD 加容差 inlier 匹配任意偏移的单张精灵，并对遮挡和出界做了鲁棒处理，最后贪心选取能解释像素的结果；
   - inlier ≥85% 记为高置信度，后续统计只用高置信度物件。
3. **人物**（`detect_characters.py`）：人物由 5 层合成，组合太多，无法整体匹配。改为分别匹配服装层和配饰层的帧（D7）。

验证方法：把反解析结果重新渲染，与原图逐像素对比，吻合率 82%–98%（中位约 92%，`scene.py`）。

### 1.4 统计规律（`semantics.py`、`stats.py`、`measure_blocks.py`、`char_stats.py`）
- **语义类别**：按素材名关键词给精灵分类，按颜色给地面分类。
- **尺寸**：
  - 双车道 5–6 格，宽路 9–11 格；
  - 人行道众数 1–3 格；
  - 立面宽 4–13 格；
  - 区块参考尺寸约 28×20 格（已和用户确认）。
- **成对关系 lift**：两类物件在 40px 内同时出现的次数，除以随机打乱标签后的期望次数。例如：
  - 红绿灯 + 红绿灯 6.2；
  - 垃圾 + 垃圾 4.2；
  - 座位 + 桌子 3.9。
- **位置分布**：每类物件脚下是什么地面、离路缘多远。例如红绿灯离路缘 1 格，路灯约 23px。
- **节拍**：等距成排检测，得到路缘设施的间距，比如 32–48px。
- **人物**：
  - 职业服装只出现在对应场所；
  - 坐姿的人 28px 内几乎都有桌子或长椅；
  - 群组大小分布：单人 85、两人 24、三人 16；
  - 密度约每 30–60 格 1 人。

  人物的主题标签记在 `character_themes.json`，每条注明证据来源。

### 1.5 评估基线（`novelty.py baseline`）
同一套指标先在参考图和反例上跑一遍，作为验收线：
- 与参考图共享的 4×4 图块窗口：不相干参考图之间为 0。
- 图内自我重复：参考图约 0，反例 0.64。最初用 4×4 图块窗口衡量，但人行道纹理本身是周期性的，会误报，后来改成“物件星座”（D13）。
- 最大空地块：参考图中位约 60 格，反例 4,211 格。

### 1.6 导出给生成器的数据
- `export_manifest.py` → `app/src/gen/data/`：
  - `sprites.json`：精灵尺寸和包围盒；
  - `autotile.json`；
  - `modular.json`：模块楼的分件和配色；
  - `characters.json`：人物图层和主题。
- `export_opaque.py` → `opaque.json`：541 张建筑精灵的不透明掩码，每 4×4 像素一位，用来判断楼后物件是否被完全挡住（D22）。

**生成器在运行时不读取任何参考图内容**，只用素材元数据，以及写进规则里的统计参数。

## 2. 生成：叙事优先的分层程序生成

代码在 `app/src/gen/`，总调度是 `generate.ts`。

### 2.1 可复现性
`rng.ts` 用 sfc32 随机数，种子先经过 cyrb128 哈希。`fork(label)` 用“原始种子 + 标签”派生出各子系统独立的随机流。这样改动一个子系统时，其余子系统的结果不变，便于逐版对照同一个种子。

### 2.2 管线（按执行顺序，顺序就是优先级）

1. **街区骨架**（`layout.ts`，D10）
   - 内部面积 560 格 ±30%，宽高比 1.05–1.9。
   - 形状有四种：矩形 / jog（单边错位）/ notch（缺角，形成小岛街区和 T 字路口）/ 两者组合。
   - 内部形状膨胀出人行道（2–3 格），再膨胀出道路（5/7 格，或 9 格宽路）。
   - 地面用 47 格 autotile 拼路缘和转角；中心虚线和人行横道由“道路连续长度”推出。
2. **建筑**（`buildings.ts`、`pack.ts`、`block.ts`、`neighbours.ts`，D9/D11/D15/D16）
   - 模块楼由屋顶、0–3 层中间层和底商拼成，各部分独立抽样，所以同类楼出现两次时外观不同（押韵而非复制）。另有单体建筑。
   - 统一的打包器：从最低行开始底边对齐放楼；面朝背面的楼留前院；非临街的楼只能是住宅。
   - 立面统一朝南。
   - 碰撞体积等于屋顶大小。屋顶以上的部分压住的地面，算作楼后的内院。
   - 邻近街区在扩展网格上打包，所以画面边缘被裁切的街区也有楼。
3. **内院逐块分配**（`yard.ts`，D12/D18/D19/D22）
   - 空地切成矩形，先切可见地面，再切被楼挡住的地面。每个矩形按规则分配用途：停车场、花园、楼前空地、过道、绿化带、杂物角、后院。
   - 停车场必须用 `findDrive` 找到一条通到马路的 2 格宽车道，找不到就不做停车场。车道会切开路缘，所以这一步必须在路缘设施之前执行。
   - 后院物件必须被楼的不透明像素完全挡住才放。草坪向楼后延伸 3 格，让花园看起来连续。
4. **通行带**（`reserveWalkways`，D17）：每段人行道预留一条 8–12px 的通行带，只有人能进入，物件不能放。
5. **功能小组**（`vignettes.ts`）
   - 每个小组都围绕一个锚点（物件“出现的理由”），是参数化语法，不是模板。部件种类、数量、左右、距离都随机，再按 1.4 的统计校准。
   - 按优先级依次放置：
     1. 人行横道 + 成对红绿灯；
     2. 巷子和广场；
     3. 公交站：候车亭 + 站牌 + 等车的人 + 垃圾桶；
     4. 店门：不同业态配不同内容，例如餐饮放桌椅和顾客，零售放立牌和盆栽；
     5. 小岛广场：局部对称；
     6. 路缘节奏带；
     7. 路边车；
     8. 井盖和道路施工；
     9. 行人。
   - **路缘节奏带**（D14/D20）：路灯按每 8–12 格一盏单独布置，灯臂朝向马路。树的间距在 3–7 格之间加权随机，偶尔缺一棵。花箱和护柱成组放在街角附近。有些街道什么都不放。
6. **放置约束**（`place.ts`）
   - 物件之间不重叠，并登记禁放区：门前、横道口、巷口、车道口、通行带。
   - 路缘设施的 footprint 四个角都必须落在人行道上。
   - 最后按脚底 y 坐标排序绘制。
7. **人物**（`people.ts`）
   - 按 CHARACTER_GENERATOR 的图层顺序合成。
   - 职业服装只由对应的小组指定（警察、邮差、工人……），其余随机便装。
   - 姿势和朝向由小组的焦点决定：坐长椅、看橱窗、面朝马路等车等。

### 2.3 输出与查看
- `main.ts` 是 Phaser 查看器：R 重新生成，G 虚化楼上层，E 导出。导出一次给出 PNG、`_ghost.png` 和 scene JSON 三个文件。
- `scripts/batch.ts`：Node 批量生成。
- `tools/render_generated.py`：Python 渲染，与 Phaser 逐像素一致率 99.5%。
- `scripts/shots.ts`：用系统自带的 Edge 点击真实导出按钮截图。

### 2.4 可解释与标注（v0.4.0，D23–D28）
- 每个物件带 `gid`（小组实例）、`reason`、`anchor`；场景 JSON 另有小组表、建筑表（外框 / 碰撞体积 / 打包原因）、区域表（为什么空）、决策轨迹。
- 所有离散随机选择都经过 `choose(label, ctx, options)`，抽法与原来相同，所以画面不变；轨迹记录流上下文、选项、权重和结果，供阶段 7 重新加权。
- 查看器的标注层（A）显示这些信息；好 / 坏标注由开发服务器写入 `references/labels/`。
- 实验功能：登记在 `exp.ts`，用独立随机流，产物带实验编号。

## 3. 评估与迭代闭环

- **自动评估**：`tools/eval_generated.py`，每个版本都跑：
  - 抄袭：与参考图共享的图块窗口、物件星座；
  - 图内自我重复、不同种子之间的重复；
  - 物件和人物的密度；
  - 最大空地块；
  - 设施站在车道上的数量、人行道中线被挤占的比例（v0.3.0 新增）。
- **人工评价为准**：
  - 用户的评价写在 `references/remarks/v<版本>/remarks.md`，每版逐条处理“需修正 / 不足”，同时保留评价中的“优点 / 特色”；
  - 指标和用户判断不一致时，改指标，不坚持指标；
  - 每版的报告是 `docs/v<版本>.md`，完成后 git tag `v<版本>`。

## 4. 被否决的主要方法（详见 NOTE.md）

| 方法 | 否决原因 |
|---|---|
| 生成式模型（扩散 / GAN） | 数据太少；像素无法保证由素材拼成；难以复现 |
| WFC / 图块马尔可夫链 | 容易拼出参考图片段；处理不了自由物件和功能关系（可能只用于地面细节） |
| 从参考图抠出小组模板，再随机摆放 | 本质上是拼贴，正是反例“复制粘贴感”的来源 |
| 学习成对势能再用 MCMC 优化摆放 | 数据噪声大，暂不作为主方法；保留为以后的填充 / 微调手段 |
| 固定节拍的路缘设施、整块复制的街区 | 用户评价为“完全重复”；物件星座重复率超过参考图上限 |
